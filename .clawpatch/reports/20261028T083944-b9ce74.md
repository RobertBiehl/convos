## high: Resuming remote ID migration can delete the migrated winner

id: fnd_sig-feat-library-4445d2d730-68a3_2d09a8f91a
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Python source src (feat_library_4445d2d730)

evidence:
- src/ai_convos/migrations.py:61 (migrate_remote_ids)
- src/ai_convos/migrations.py:70-83 (migrate_remote_data)
- src/ai_convos/migrations.py:91 (migrate_remote_data)

Winner selection prioritizes the current proof over an already canonical physical ID. Consequently, a legacy-ID row can win while an older row at its destination ID loses. The data phase deletes the destination loser, renames the winner to that destination, and commits. Until line 91, the durable migration stage remains 'data' or 'data_direct'. Replaying that phase after interruption executes the same loser deletion against the destination ID, which now contains the winner. The subsequent UPDATE finds no row at the winner's old ID, permanently removing the current body from the active archive. The direct FTS updates have the same replay hazard.

recommendation:
Make each committed rewrite resumable by atomically recording batch completion and skipping completed batches, or retain staged winner bodies and restore destinations idempotently. Apply the same protection to direct FTS rewrites.

test analysis:
The supplied test excerpts cover backups, schema upgrades, and replay convergence, but do not exercise interruption after a committed ID rewrite where the losing row originally occupied the winner's destination ID.

suggested regression test:
Build the canonical-loser/legacy-winner fixture, interrupt immediately after the message rewrite commits, and resume. Assert that the latest message body, origin, child references, and FTS entry survive; repeat resume to prove idempotence.

minimum fix scope:
src/ai_convos/migrations.py data-phase checkpointing and an interruption regression test.

repro:
Create two received representations of one logical message: an older revision already at the canonical ID and the current revision at a legacy ID. Run migration until the message rewrite at line 83 commits, then interrupt before line 91. Resume migrate_remote_data using the retained staging tables. The canonical message is deleted and cannot be recreated from those tables.

## medium: Audit suppresses required proof heads across workspaces

id: fnd_sig-feat-library-3be334928b-4263_2e5049dd6f
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Python source apps/remote/src (feat_library_3be334928b)

evidence:
- apps/remote/src/ai_convos_remote/projection.py:182-187 (_audit_rows)
- docs/invariants.md:112-117
- tests/test_remote_projection.py:115-122 (test_audit_detects_missing_body_even_without_surviving_origin)

The fallback inventory identifies surviving proof heads using a NOT EXISTS successor query scoped by kind, source row and author, but not workspace. Revision IDs deliberately exclude workspace, and the documented contract says a proof is superseded only within its own workspace. A successor in workspace A therefore suppresses an independently current proof in workspace B. If B's origin and retained body are missing, this fallback skips the proof and the audit can incorrectly report zero unavailable bodies.

recommendation:
Include the proof's origin workspace in the successor correlation used to discover audit requirements.

test analysis:
The included missing-origin regression uses one workspace. The included cross-workspace retirement tests publish deletion successors in both workspaces and do not exercise an independently current proof whose origin is missing.

suggested regression test:
Extend missing-origin audit coverage with identical initial revisions in two workspaces and a successor in only one. Assert that losing the other workspace's current body produces an unavailable result.

minimum fix scope:
The head-selection query in _audit_rows and one cross-workspace audit regression.

repro:
Publish identical initial revisions for one author and row in workspaces A and B. Publish a changed successor only in A. Remove B's origin and old retained body while preserving its proof and A's current projection. Run audit_rows with local_user supplied; B's missing current body is omitted.

## medium: Pre-existing: proxy URL rewrites split Memory repository scopes

id: fnd_sig-feat-library-fdfbcb4ae4-9dba_0e54dccc4d
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Python source apps/memory/src (feat_library_fdfbcb4ae4)

evidence:
- apps/memory/src/ai_convos_memory/__init__.py:50-59 (_repository)
- apps/memory/src/ai_convos_memory/__init__.py:66-93 (_scope / _bind_scope)
- apps/memory/src/ai_convos_memory/__init__.py:239-257 (remember_data)

Memory hashes `git remote get-url origin`, which includes insteadOf transport rewriting. The proxy port therefore becomes repository identity despite an unchanged configured origin. After a port change, _scope rejects the existing checkout binding; _bind_scope finds no matching repository and replaces that binding with a suffixed scope. Existing canonicals remain in the old scope, while subsequent scoped reads and writes use the new scope. Previously saved memories disappear from that checkout's current scope, and remembering identical content creates another canonical because its ID includes scope. This is pre-existing in optional Memory's separate identity recipe, not a regression introduced by the core archive identity fix.

recommendation:
Handle this as a separate scoped Memory migration decision. Derive repository identity from configured canonical origin evidence before transport rewriting, and define a backed-up migration for existing bindings and affected scope references. Do not merely replace the hash input: that would itself change persisted repository identities and trigger the same scope split.

test analysis:
No Memory tests were included in the review context. Coverage of transport rewrite changes and persisted scope continuity cannot be established from the supplied excerpts.

suggested regression test:
Use the isolated checkout and ledger above; assert repository identity, bound scope, and canonical ID remain stable across proxy-port changes and cache clears. Add migration coverage proving existing memories and their links remain accessible, while genuinely different configured origins remain isolated.

minimum fix scope:
Separate optional Memory identity and ledger-migration change covering _repository, repository_scopes, affected scope references, and synthetic continuity/isolation tests.

repro:
Synthetic regression procedure, not executed here: create an isolated temporary Git checkout and temporary Memory ledger, with global/system Git configuration disabled. Configure origin as https://code.example.com/team/project.git and local url.http://127.0.0.1:41001/session/.insteadOf=https://code.example.com/. Point CONVOS_MEMORY_DB at the temporary ledger. Clear _repository's cache, record its repository ID, and call remember_data('synthetic memory', scope=str(checkout)). Replace the rewrite with url.http://127.0.0.1:41002/session/.insteadOf=https://code.example.com/, then clear the cache again. The repository ID changes although remote.origin.url is unchanged. Repeat remember_data with identical content: its scope gains a repository suffix and its canonical ID changes. Verify _scope(checkout) now returns the new scope while the original canonical still belongs to the old scope. No network access or live archive is needed.
